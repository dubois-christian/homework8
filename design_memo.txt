Design Memo

I chose a hash table because a contact manager needs to find phone numbers quickly.
Rather than checking every contact in a list, it uses the person's name to choose
an index in an array. When names are spread fairly evenly across the table,
looking up a contact usually takes only a few steps. My hash function uses ord()
to turn each character into a number, combines those numbers, and uses the table
size to keep the index within the array.

Different names can land at the same index, so I used separate chaining to handle
collisions. Each position in the array holds the start of a linked list. When I
add a contact, the program checks that list for the name first. If it finds the
name, it updates the phone number. Otherwise, it adds a new node. Searching
follows the same list and returns None if the contact is missing.

An engineer might choose a hash table when exact lookups matter more than keeping
items sorted. A list is simpler for small collections, while a balanced tree is
useful for sorted data or range searches. This table has a fixed size, so adding
many contacts can make its chains longer and slow searches down. If every name
lands in one bucket, a search can take as long as scanning a list.
